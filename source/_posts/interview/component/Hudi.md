## 美团的Hudi是什么

结合你之前的美团数仓升级背景，你问的 **Hudi**（Apache Hudi）非常关键。在面试中这是一个很好的加分项。

简单说，Hudi 是美团技术团队在大数据领域深度使用并回馈社区的一个**数据湖框架**，全称是 **H**adoop **U**pserts and **I**ncrementals（增量更新） **D**ata-lake **I**ngest。

你可以这样理解它的角色：它是为了解决你之前提到的“烟囱式开发”和“T+2小时延迟”这类问题的核心利器。

------

### 1. 它解决了传统数仓的什么痛点？

在 Hive 时代，你做的数仓表很难直接进行 Update（更新）或 Delete（删除），只能做 Insert Overwrite（全量覆盖）。这会带来你遇到的三个问题：

- **更新效率低**：比如一个订单的状态从“已支付”变为“已退款”，在Hive里可能要重写整个分区，耗费数小时。
- **无法近实时入湖**：想把数据库（MySQL）的变更日志（Binlog）在分钟级同步到数仓，传统Hive做不到。
- **数据回溯麻烦**：查询某个时间点的数据（比如对账）非常困难。

**Hudi的出现，就是让 Hadoop 体系的数据湖拥有类似数据库的能力。**

------

### 2. Hudi 的核心能力（对应你简历中的亮点）

如果面试官让你展开讲讲，可以从这三个价值点来回答，正好对应你的项目经验：

**① 支持行级别的更新/删除**
Hudi 不写全量，只写增量。当订单状态变化时，Flink/Spark 流式写入 Hudi，在分钟级更新那一条订单的状态，**而不是重跑整个小时级分区**。
**对应你的成果**：这直接帮助你把订单报表产出从 T+2 小时缩短到了 **T+45 分钟甚至更短**。

**② 无缝支持 CDC 数据同步**
你项目中用到的 Flink 实时数据同步，最典型的落地场景就是 **Flink CDC + Hudi**。MySQL 的 Binlog 被 Flink 解析后，直接写进 Hudi 表，保证了数仓和业务库的数据一致性。这帮你解决了“实时核心指标”的底层存储问题。

**③ 时间旅行**
Hudi 保存了数据每次的提交版本，你可以随时回溯到历史某个版本的数据。在统一指标口径时，这个能力可以作为最终的数据仲裁依据，看过去某天数据到底是多少。

你在美团做数仓迭代时，很可能用过或接触过 Hudi。它是美团乃至国内互联网公司构建**实时数仓**和**流批一体**架构的关键组件。整个流程一般是：
**线上业务 MySQL（订单/用户）** → **Flink CDC（解析Binlog）** → **Kafka（消息中转）** → **Flink/Spark Streaming（清洗加工）** → **Hudi（数仓存储）**

## Apache Hudi 引擎全解析：核心原理与深度优化

Apache Hudi（Hadoop Upserts Deletes and Incrementals）是**专为数据湖设计的开源存储框架**，核心解决了传统数据湖（Hive）无法高效处理**增量更新、变更数据捕获（CDC）和 ACID 事务**的痛点。它通过独特的文件组织、索引机制和 MVCC 设计，实现了 "**流批一体**" 的数据存储能力，是美团外卖数仓 3.0 升级的核心技术底座之一。

### 一、Hudi 核心定位与解决的问题

#### 1. 传统数据湖的致命缺陷

在 Hudi 出现之前，数据湖主要基于 Hive 构建，存在以下无法解决的问题：

- **更新效率极低**：更新一条记录需要重写整个分区或整个表，大表更新耗时数小时
- **数据延迟高**：只能支持 T+1 级别的数据更新，无法满足实时业务需求
- **没有事务保证**：写入过程中可能出现数据不一致或脏读
- **无法增量查询**：只能全量扫描数据，无法高效获取变更数据
- **小文件问题严重**：频繁写入会产生大量小文件，严重影响查询性能

#### 2. Hudi 的核心价值

Hudi 在数据湖之上提供了**数据库级别的能力**，同时保留了数据湖的低成本、高扩展性优势：

- **高效 Upsert/Delete**：支持行级别的更新和删除，无需重写整个文件
- **ACID 事务**：保证数据写入的原子性、一致性、隔离性和持久性
- **增量查询**：可以高效获取某个时间点之后的所有变更数据
- **时间旅行**：可以查询任意历史时间点的数据快照
- **流批一体**：同一套数据同时支持流式写入和批量查询

### 二、Hudi 核心架构与基本概念

#### 1. 整体架构

Hudi 采用**分层架构**，从上到下分为：

- **API 层**：提供 Spark、Flink、Java 等多种语言的 API
- **核心层**：实现了事务管理、索引、写入、查询等核心功能
- **存储层**：基于 HDFS、S3 等分布式文件系统存储数据

#### 2. 关键基本概念

##### （1）Hoodie Key（Hudi 主键）

Hudi 表的唯一标识，由`recordKey`（记录主键）+ `partitionPath`（分区路径）组成。一旦记录被写入，它的 Hoodie Key 到文件组的映射关系就永远不会改变，这是 Hudi 实现高效 Upsert 的基础Apache Hudi。

##### （2）File Group（文件组）

Hudi 表的基本存储单元，每个文件组对应一个唯一的`fileId`。一个文件组包含多个`File Slice`（文件切片），每个切片对应一个版本的数据。

##### （3）File Slice（文件切片）

一个文件切片由一个**Base File**（基础文件，Parquet 格式）和多个**Log File**（日志文件，Avro 格式）组成。

- Base File：存储列式数据，是文件切片的基础
- Log File：存储增量更新数据，只有 MOR 表才有

##### （4）Timeline（时间线）

Hudi 的核心机制之一，用于管理表的所有操作。每个操作都对应一个`Instant`（时刻），包含操作类型、时间戳和状态。

- **操作类型**：COMMIT（提交）、CLEANS（清理）、COMPACTION（压缩）、ROLLBACK（回滚）
- **状态**：REQUESTED（已请求）、INFLIGHT（进行中）、COMPLETED（已完成）

Timeline 保证了 Hudi 的 ACID 事务和时间旅行能力，用户可以基于 Timeline 查询任意历史版本的数据。

### 三、Hudi 两种核心表类型详解

Hudi 提供了两种表类型，分别适用于不同的读写场景，这是 Hudi 最具特色的设计之一。

#### 1. Copy On Write（COW，写时复制）

##### 工作原理

- 只有 Base File（Parquet 格式），没有 Log File
- 写入数据时，找到包含待更新记录的 Base File，复制一份并在副本上进行修改，生成新的 Base File 版本
- 旧版本的 Base File 会被保留，用于时间旅行查询
- 查询时直接读取最新版本的 Base File，无需任何合并操作

##### 优缺点

|                优点                 |                  缺点                  |
| :---------------------------------: | :------------------------------------: |
| 查询性能极高，与普通 Parquet 表一致 |  写入性能差，更新操作需要重写整个文件  |
|     数据一致性好，没有脏读问题      | 写入放大严重，频繁更新会产生大量小文件 |
|     管理简单，无需后台压缩任务      |          不适合高并发写入场景          |

##### 适用场景

- 读多写少的场景
- 批量更新为主，更新频率低
- 对查询性能要求高

#### 2. Merge On Read（MOR，读时合并）

##### 工作原理

- 同时包含 Base File（Parquet 格式）和 Log File（Avro 格式）
- 写入数据时，直接将增量数据追加到 Log File 中，无需修改 Base File
- 后台异步执行`Compaction`（压缩）任务，将 Log File 与 Base File 合并生成新的 Base File 版本
- 查询时有两种视图：
  - **Read Optimized View（读优化视图）**：只读取 Base File，不合并 Log File，查询性能高，但数据不是最新的
  - **Realtime View（实时视图）**：实时合并 Base File 和 Log File，返回最新数据，但查询性能较低

##### 优缺点

|                优点                |                缺点                |
| :--------------------------------: | :--------------------------------: |
| 写入性能极高，更新操作只需追加日志 | 查询性能较低，实时视图需要合并操作 |
|      写入放大小，适合频繁更新      |   管理复杂，需要配置后台压缩任务   |
|         支持近实时数据查询         |         数据一致性相对较弱         |

##### 适用场景

- 写多读少的场景
- 高并发写入，更新频率高
- 对数据时效性要求高，需要近实时查询

#### 3. COW vs MOR 核心对比表

|    维度    |         COW          |          MOR           |
| :--------: | :------------------: | :--------------------: |
|  写入性能  |    低（重写文件）    |     高（追加日志）     |
|  查询性能  | 高（直接读 Parquet） | 中（实时视图需要合并） |
|  写入放大  |          大          |           小           |
|  数据延迟  |     高（分钟级）     |       低（秒级）       |
|  存储成本  |   高（多版本文件）   |   中（日志文件较小）   |
| 管理复杂度 |          低          |           高           |
|  典型应用  |    离线数仓、报表    |   实时数仓、CDC 同步   |

### 四、Hudi 核心特性

#### 1. ACID 事务

Hudi 通过 Timeline 和 MVCC（多版本并发控制）机制实现了 ACID 事务：

- **原子性**：写入操作要么全部成功，要么全部失败
- **一致性**：事务提交后，所有查询都能看到一致的数据视图
- **隔离性**：多个写入操作可以并发执行，互不干扰
- **持久性**：一旦事务提交，数据就不会丢失

#### 2. 增量查询

Hudi 支持基于 Timeline 的增量查询，可以高效获取某个时间点之后的所有变更数据。这对于构建增量 ETL 管道非常有用，可以避免全量扫描数据，大幅提升计算效率。

#### 3. 时间旅行

Hudi 保留了数据的所有历史版本，用户可以查询任意历史时间点的数据快照。这对于数据修复、审计和回溯分析非常有价值。

#### 4. 自动小文件管理

Hudi 内置了自动小文件合并功能，可以在写入时或后台异步合并小文件，避免小文件问题对查询性能的影响。

#### 5. 并发控制

Hudi 支持多种并发控制策略，包括乐观并发控制（OCC）和悲观并发控制（PCC），可以满足不同场景的并发写入需求。

### 五、Hudi 深度优化原理

#### 1. 写入优化

##### （1）索引机制（Hudi 写入性能的核心）

索引是 Hudi 实现高效 Upsert 的关键，它负责将 Hoodie Key 映射到对应的文件组。没有索引，Hudi 需要扫描整个表来找到待更新的记录，性能会非常差Apache Hudi。

Hudi 支持多种索引类型，各有优缺点：

|         索引类型          |                           工作原理                           |          优点          |           缺点           |         适用场景         |
| :-----------------------: | :----------------------------------------------------------: | :--------------------: | :----------------------: | :----------------------: |
| **Simple Index（默认）**  |   读取所有 Base File 的主键和分区路径，与待写入数据做 Join   | 实现简单，无需额外存储 | 性能差，需要扫描所有文件 |      小表、测试环境      |
|      **Bloom Index**      | 每个 Base File 的页脚存储一个布隆过滤器，用于快速判断文件是否包含某个主键 |  性能较好，存储开销小  | 存在误判率，需要二次验证 |  中大型表、主键分布均匀  |
|  **Global Bloom Index**   |        与 Bloom Index 类似，但支持跨分区的主键唯一性         |      支持全局主键      |  性能比 Bloom Index 差   |    需要全局去重的场景    |
|     **Bucket Index**      |      对主键进行哈希计算，将记录路由到固定的桶（文件组）      | 性能极高，常数时间查找 | 桶数量固定，无法动态调整 |     大表、高并发写入     |
| **Record Index（0.14+）** |             将主键到文件组的映射存储在元数据表中             | 性能最好，支持全局主键 |    元数据表存储开销大    | 超大型表、对性能要求极高 |

**美团实践**：美团在 Beluga 引擎中主要使用 Bucket Index，因为它最适合高并发的 CDC 数据同步场景。他们还对 Bucket Index 进行了优化，支持动态调整桶数量，解决了原始 Bucket Index 桶数量固定的问题。

##### （2）异步写入与预写日志（WAL）

Hudi 支持异步写入和预写日志机制，可以提高写入的可靠性和性能：

- 预写日志：在写入数据之前，先将操作记录到 WAL 中，防止写入过程中出现故障导致数据丢失
- 异步写入：将数据写入和提交操作分离，提高写入吞吐量

##### （3）批量写入与内存优化

Hudi 支持批量写入，可以将多个小的写入请求合并成一个大的请求，减少网络 IO 和磁盘 IO。同时，Hudi 对内存使用进行了优化，避免了频繁的 GC 和内存溢出。

#### 2. 查询优化

##### （1）数据跳过（Data Skipping）

Hudi 利用元数据表中的列统计信息（min/max、null count 等）和布隆过滤器，在查询时跳过不包含所需数据的文件和分区，大幅减少扫描的数据量Apache Hudi。

##### （2）向量化查询

Hudi 支持向量化查询，可以批量处理数据，提高查询性能。同时，Hudi 与 Spark、Flink 等计算引擎深度集成，利用引擎的向量化执行能力。

##### （3）读优化视图与实时视图

Hudi 提供了两种查询视图，用户可以根据自己的需求选择：

- 读优化视图：适合对查询性能要求高，对数据时效性要求不高的场景
- 实时视图：适合对数据时效性要求高，能接受一定查询延迟的场景

#### 3. 存储优化

##### （1）列式存储与压缩

Hudi 的 Base File 使用 Parquet 列式存储格式，支持多种压缩算法（Snappy、Gzip、ZSTD 等），可以大幅减少存储成本。同时，列式存储也有利于提高查询性能。

##### （2）日志文件优化

Hudi 的 Log File 使用 Avro 行式存储格式，适合快速追加写入。同时，Hudi 对 Log File 进行了优化，支持批量写入和压缩。

##### （3）自动清理与归档

Hudi 会自动清理过期的文件版本和日志文件，回收存储空间。同时，Hudi 支持将历史数据归档到低成本的存储介质中，进一步降低存储成本。

#### 4. 元数据优化

Hudi 0.10 + 引入了**元数据表（Metadata Table）**，将原来分散在各个文件中的元数据集中存储在一个 Hudi 表中，大幅提升了元数据操作的性能Apache Hudi。

元数据表包含以下分区：

- `files`：存储所有文件的信息（文件名、大小、状态等）
- `column_stats`：存储所有列的统计信息（min/max、null count 等）
- `bloom_filter`：存储所有文件的布隆过滤器
- `record_index`：存储主键到文件组的映射（Record Index）

元数据表的引入带来了以下好处：

- 避免了直接访问文件系统的大量 list 操作，提升了文件列表性能
- 集中存储列统计信息和布隆过滤器，提升了数据跳过的效率
- 支持 Record Index，大幅提升了 Upsert 性能

### 六、美团 Beluga 引擎：基于 Hudi 的深度改造

美团外卖数仓 3.0 升级中，基于 Apache Hudi 0.12 版本深度改造了内部存储引擎**Beluga**，解决了原生 Hudi 在大规模生产环境中的多个痛点。

#### 1. 改造背景

原生 Hudi 在美团的大规模使用中遇到了以下问题：

- 单层 Bucket 设计，文件数量上限有限
- Compaction 重缩放不透明，影响性能
- Timeline 存储在 HDFS 上，效率低
- 缺乏原生的 CDC 支持
- 表快照精准切分困难

#### 2. 核心改造点

##### （1）两层分桶设计

将原来的单层 Bucket 改为两层分桶设计，面向流、批不同负载进行优化，解决了文件数量上限的问题。

##### （2）独立 MetaServer 服务

将原来的客户端侧元数据管理改为独立的 MetaServer 服务，负责维护 Timeline、Instant、Bucket 等组织关系，以及管理 Compaction、Clean 等表服务，大幅提升了元数据操作的性能和可靠性。

##### （3）一表三模式

支持 "全量表、快照表、增量表" 三种模式在同一张表中同时存在，满足不同业务场景的需求：

- 全量表：存储所有历史数据
- 快照表：存储某个时间点的完整数据快照
- 增量表：存储某个时间点之后的变更数据

##### （4）原生 CDC 支持

基于 HBase（KV）生产 Changelog，提供原生的 CDC 能力，支持增量数据的高效同步和消费。

#### 3. 落地效果

- 大表合并时间从 2-3 小时缩短到 1 小时以内
- 数据延迟从 T+1 降低到分钟级
- 计算资源节省 30% 以上
- 存储资源节省 25% 以上

### 七、Hudi vs Iceberg vs Delta Lake

目前主流的数据湖存储框架有三个：Apache Hudi、Apache Iceberg 和 Delta Lake。它们各有优缺点，适用于不同的场景。

|    维度    |                  Hudi                  |                Iceberg                 |               Delta Lake               |
| :--------: | :------------------------------------: | :------------------------------------: | :------------------------------------: |
|  创始公司  |                  Uber                  |                Netflix                 |               Databricks               |
|  核心优势  | 高效 Upsert/Delete、流批一体、增量查询 | 完善的 Schema 进化、分区进化、查询优化 | 与 Spark 深度集成、易用性好、ACID 事务 |
|  写入性能  |             最好（MOR 表）             |                  中等                  |                  较差                  |
|  查询性能  |                   好                   |                  最好                  |                   好                   |
|  生态支持  |    好（Spark、Flink、Hive、Presto）    |          最好（几乎所有引擎）          |           好（主要是 Spark）           |
| 社区活跃度 |                   高                   |                   高                   |                   高                   |
|  适用场景  |     实时数仓、CDC 同步、高并发写入     |   离线数仓、即席查询、数据湖统一存储   |     机器学习、数据科学、Spark 生态     |

### 八、总结

Apache Hudi 是目前数据湖领域最成熟、最强大的存储框架之一，它通过独特的文件组织、索引机制和 MVCC 设计，解决了传统数据湖无法高效处理增量更新和实时数据的问题。

美团外卖数仓 3.0 升级中，基于 Hudi 深度改造的 Beluga 引擎，成功实现了数仓从 "离线全量" 到 "流批一体" 的转型，大幅提升了数据时效性和开发效率，同时降低了资源成本。

对于大多数企业来说，如果你的业务需要处理大量的增量更新和实时数据，那么 Hudi 是一个非常好的选择。如果你的业务主要是离线分析和即席查询，那么 Iceberg 可能更适合你。如果你主要使用 Spark 生态，并且对易用性要求较高，那么 Delta Lake 也是一个不错的选择。

## 问题

### MOR 和 COW 表是什么

MOR（Merge On Read，读时合并）和 COW（Copy On Write，写时复制）是 Apache Hudi 提供的两种核心表存储类型，二者的核心差异是**数据更新的合并时机不同**，本质是「写入性能」与「查询性能」的权衡，也是实时数仓、数据湖方向的高频面试考点。

------

#### 一、COW（Copy On Write）：写时复制

**核心逻辑**：数据写入（新增 / 更新）时立刻完成数据合并，写入过程中直接生成最终的列式存储文件，查询时无需额外计算。

##### 工作原理

1. Hudi 的基础数据以 Parquet 列式格式的`Base File`（基础文件）按分区存储；
2. 当有新数据写入或更新时，定位到需要修改的 Base File，将其完整复制一份，与新数据在内存中合并，生成一个全新的 Base File；
3. 旧 Base File 保留为历史版本，新文件原子替换生效；查询时直接读取最新的 Base File 即可，和读取普通 Hive 表无差异。

##### 核心特点

- **写慢读快**：写入时需要复制、重写整个文件，更新越频繁、文件越大，写入开销越高；查询时直接读 Parquet 文件，无额外计算开销，性能与离线表一致。
- **存储放大明显**：每次更新都会重写整个文件，产生大量历史版本文件，存储膨胀较快。
- **实现简单**：没有日志文件、后台合并等复杂机制，运维成本低。

##### 适用场景

- 读多写少、更新频率低的场景；
- 纯追加写入、几乎没有更新的明细数据（如用户行为日志）；
- 批量写入为主、对查询性能要求极高的场景。

------

#### 二、MOR（Merge On Read）：读时合并

**核心逻辑**：写入时只追加日志文件，不立刻合并基础数据；查询时实时合并基础文件与增量日志，返回最新结果，合并操作后置到查询阶段。

##### 工作原理

1. 基础数据同样是 Parquet 格式的`Base File`；
2. 实时写入的增量数据（新增 / 更新）以行存 Avro 格式写入`Log File`（日志文件），写入速度极快，不需要修改原有 Base File；
3. **查询读取**时，引擎会同时加载对应分区的 Base File 和所有未合并的 Log File，在内存中做合并、去重，返回最新的快照数据；
4. **后台 Compaction（压缩合并）**：Hudi 会异步定时执行 Compaction 任务，将累积的 Log File 合并到 Base File 中，生成新的基础文件，减少后续查询的合并开销。

##### 核心特点

- **写快读慢**：写入只追加日志，延迟极低、吞吐极高，适合高频实时更新；查询需要实时合并日志，有额外计算开销，查询延迟高于 COW 表。
- **存储更友好**：日志文件体积小，只有合并时才会重写基础文件，存储放大远低于 COW。
- **机制更复杂**：需要管理 Compaction 策略，查询性能依赖合并频率，运维成本更高。

##### 适用场景

- 写频繁、实时更新要求高的场景（如 Binlog CDC 同步的业务表）；
- 高吞吐实时写入的明细层、汇总层；
- 对写入延迟敏感、查询可容忍轻微开销的实时数仓场景。

------

#### 三、核心差异对比表

表格

| 对比维度     | COW（写时复制）                | MOR（读时合并）                     |
| ------------ | ------------------------------ | ----------------------------------- |
| 合并时机     | 写入时合并，写时重写 Base File | 查询时实时合并，后台异步 Compaction |
| 写入性能     | 低（更新时需复制整文件）       | 高（仅追加日志文件）                |
| 查询性能     | 极高（直接读 Parquet）         | 中等（需合并 Base+Log）             |
| 更新开销     | 高，文件越大开销越大           | 低，仅追加日志                      |
| 存储放大     | 高，每次更新生成新文件         | 低，日志文件体积小                  |
| 文件格式     | 仅 Parquet Base File           | Parquet Base File + Avro Log File   |
| 运维复杂度   | 低，机制简单                   | 高，需管理 Compaction 策略          |
| 数仓典型分层 | 流量日志 DWD、静态维度 DIM     | 交易 / 履约 DWD、DWS 汇总层         |

------

#### 四、实时数仓分层的选型实践

对应美团增量数仓的分层设计，选型逻辑非常明确：

1. DWD 层
   - 流量、埋点等纯追加的明细表：用 COW 表，写入以追加为主，查询性能好；
   - 订单、配送、退款等高频更新的事务型明细表：用 MOR 表，承接 Binlog 的高频 Upsert，保证实时写入性能。
2. DIM 层
   - 商家、商品等更新频繁的维度表：一般用 MOR 表，实时同步 CDC 变更；
   - 地域、编码等几乎不变的静态维度：用 COW 表即可。
3. DWS 层
   - 分钟 / 小时级增量聚合的汇总表：几乎都用 MOR 表，聚合结果实时 Upsert 更新，后台定期合并优化查询性能。

------

#### 五、面试高频延伸考点

1. **MOR 表的 Compaction 策略怎么设置？** 生产环境普遍用异步 Compaction，触发策略包括：按时间周期（如每小时一次）、按日志文件大小 / 数量阈值触发；大促高峰时段可暂停 Compaction 避免资源争抢。
2. **MOR 表查询太慢怎么优化？** 提高 Compaction 频率减少未合并日志量；热点分区提前预合并；针对高频查询场景同步一份到 Doris/ClickHouse 等 OLAP 引擎加速。
3. **为什么不全部用 MOR？** 纯追加、读多写少的场景，COW 的查询性能更高、运维更简单，没有必要引入 MOR 的复杂度；只有高频更新场景 MOR 才有显著优势。
4. **COW 表的写放大问题怎么缓解？** 控制单个 Base File 的大小（如 128MB），避免文件过大；减少小批量高频更新，尽量批量写入；合理设置历史版本保留数，定期清理旧版本。
