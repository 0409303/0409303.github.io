## 一、CI/CD 相关问题（最高频）

### 1. 你在微软搭建的大数据任务 CI/CD 流水线具体是怎么设计的？包含哪些环节？

**参考答案**：

我搭建的是一套**面向大数据任务的全自动化 CI/CD 流水线**，基于 GitLab CI 实现，主要包含以下 6 个环节：

1. **代码提交阶段**：开发人员提交代码到 GitLab，自动触发流水线
2. **静态代码检查阶段**：使用 ScalaStyle、SQLFluff 等工具对 Scala 代码和 SQL 代码进行静态检查，不符合规范的代码会被拦截
3. **单元测试阶段**：运行所有的单元测试和集成测试，测试覆盖率要求达到 80% 以上
4. **打包构建阶段**：使用 Maven 将代码打包成 JAR 包，同时构建 Docker 镜像并推送到私有镜像仓库
5. **部署阶段**：使用 Helm 将应用部署到 Kubernetes 集群，支持开发、测试、生产三个环境的一键部署
6. **验收阶段**：自动运行验收测试脚本，验证任务的运行结果是否符合预期，验收通过后自动发布到生产环境

通过这套流水线，我们将大数据任务的上线周期从原来的 3 天缩短到了 4 小时，同时将线上问题率降低了 70%。

### 2. 大数据任务的 CI/CD 和传统软件的 CI/CD 有什么不同？你遇到了哪些特殊的挑战？

**参考答案**：

大数据任务的 CI/CD 和传统软件的 CI/CD 最大的不同在于**数据依赖和环境依赖**。传统软件的 CI/CD 只需要关注代码本身，而大数据任务的 CI/CD 还需要关注数据的正确性和环境的一致性。

我遇到的主要挑战有：

1. **测试数据难以获取**：生产环境的数据量太大，无法在测试环境完整复制。我们的解决方案是使用数据脱敏工具，从生产环境抽取一小部分真实数据，经过脱敏后作为测试数据。
2. **环境一致性难以保证**：大数据任务依赖很多外部系统，比如 HDFS、Hive、Kafka 等，测试环境和生产环境的配置经常不一致。我们的解决方案是使用 Docker 和 Kubernetes 将所有依赖都打包到镜像中，保证环境的一致性。
3. **测试用例难以编写**：大数据任务的输出结果往往是大量的数据，很难用传统的断言方式进行验证。我们的解决方案是编写数据校验脚本，对比任务运行结果和预期结果的差异，只有当差异在允许范围内时才认为测试通过。

### 3. 你们的 CI/CD 流水线是如何处理数据回滚的？如果一个任务上线后出现问题，你会怎么处理？

**参考答案**：

我们设计了**三级回滚机制**，确保在任务出现问题时能够快速恢复：

1. **代码回滚**：如果是代码问题，直接在 GitLab 上回滚到上一个稳定版本，流水线会自动重新构建和部署
2. **镜像回滚**：如果是镜像问题，直接在 Kubernetes 上回滚到上一个稳定的镜像版本
3. **数据回滚**：如果任务已经产生了错误的数据，我们会使用数据备份恢复到任务运行前的状态，然后重新运行任务

同时，我们建立了严格的发布流程：

- 所有任务必须先在测试环境运行 24 小时，验证无误后才能发布到生产环境
- 生产环境发布采用灰度发布策略，先发布 10% 的流量，观察 1 小时没有问题后再全量发布
- 发布后有专人值守 2 小时，监控任务的运行状态和数据质量

### 4. 你在搭建 CI/CD 流水线的过程中遇到过哪些比较棘手的问题？你是怎么解决的？

**参考答案**：

最棘手的问题是**Spark 任务在 Kubernetes 上的资源调度问题**。刚开始的时候，Spark 任务经常因为资源不足而失败，或者因为资源分配不合理导致性能很差。

我的解决方案是：

1. 首先，我们对所有的 Spark 任务进行了性能测试，统计出每个任务需要的 CPU、内存和磁盘资源
2. 然后，我们在 Kubernetes 上为 Spark 任务创建了专门的资源池，保证 Spark 任务有足够的资源
3. 接着，我们开发了一个动态资源调度插件，能够根据任务的实际运行情况自动调整资源分配
4. 最后，我们建立了资源监控和告警机制，当资源使用率超过阈值时会自动告警

通过这些措施，我们将 Spark 任务的失败率从原来的 20% 降低到了 1% 以下，同时资源利用率提高了 40%。

## 二、容器化相关问题

### 1. 你们为什么选择使用 Docker 和 Kubernetes 来部署大数据任务？和传统的部署方式相比有什么优势？

**参考答案**：

我们选择 Docker 和 Kubernetes 主要是因为它们能够解决传统部署方式的以下几个痛点：

1. **环境一致性问题**：传统的部署方式需要在每台服务器上手动安装和配置依赖，经常出现 "在我电脑上能跑，在服务器上跑不了" 的问题。Docker 将所有依赖都打包到镜像中，保证了环境的一致性。
2. **资源利用率低**：传统的部署方式通常是一个任务占用一台服务器，资源利用率很低。Kubernetes 能够将多个任务调度到同一台服务器上，大大提高了资源利用率。
3. **扩展性差**：传统的部署方式很难快速扩展，当任务需要更多资源时，需要手动添加服务器。Kubernetes 支持自动扩缩容，能够根据任务的负载自动调整资源。
4. **运维成本高**：传统的部署方式需要运维人员手动管理大量的服务器，运维成本很高。Kubernetes 提供了自动化的运维能力，能够自动处理服务器故障和任务重启。

在我们的项目中，使用 Docker 和 Kubernetes 后，服务器资源利用率从原来的 20% 提高到了 60%，运维成本降低了 50%。

### 2. 容器化部署 Spark 任务有哪些挑战？你是怎么解决的？

**参考答案**：

容器化部署 Spark 任务的主要挑战有：

1. **镜像体积过大**：Spark 镜像通常包含了完整的 Spark 发行版和所有依赖，体积超过 1GB，导致镜像拉取速度很慢。我们的解决方案是使用多阶段构建，只保留运行时需要的文件，将镜像体积减小到了 500MB 以下。
2. **网络性能问题**：Kubernetes 的网络性能比物理机差，对于网络密集型的 Spark 任务影响很大。我们的解决方案是使用 HostNetwork 模式，让 Pod 直接使用宿主机的网络，网络性能提升了 30% 以上。
3. **本地磁盘空间不足**：Spark 任务在运行过程中会产生大量的临时数据，很容易导致 Pod 的本地磁盘空间不足。我们的解决方案是将临时数据存储到宿主机的本地磁盘上，而不是 Pod 的容器磁盘上。
4. **动态资源分配问题**：Spark 的动态资源分配机制在 Kubernetes 上不能很好地工作。我们的解决方案是开发了一个自定义的资源调度器，能够根据任务的实际运行情况动态调整 Executor 的数量。

### 3. 你们的 Spark 镜像具体是怎么构建的？包含哪些内容？

### 2. 大数据任务的 CI/CD 和传统软件的 CI/CD 有什么不同？你在微软遇到了哪些特殊的挑战？

**参考答案**：

大数据任务的 CI/CD 和传统软件的 CI/CD 最大的不同在于**数据依赖、环境依赖和计算规模**。传统软件的 CI/CD 只需要关注代码本身，而大数据任务的 CI/CD 还需要关注数据的正确性、环境的一致性以及大规模分布式计算的稳定性。

在微软处理全球 PB 级搜索日志的场景下，我遇到的主要挑战有：

1. **测试数据获取与脱敏难题**：生产环境每天产生 PB 级数据，无法在测试环境完整复制，而且涉及全球用户隐私数据，有严格的 GDPR 合规要求。我们的解决方案是开发了基于**Azure Purview**的自动化数据脱敏工具，从生产环境抽取 1% 的真实数据，经过动态脱敏和数据合成后作为测试数据，既保证了数据的真实性，又符合合规要求。
2. **跨区域环境一致性问题**：我们的任务需要部署在全球 10 个 Azure 区域，每个区域的网络、存储和计算环境都有差异。我们的解决方案是使用**Terraform**进行基础设施即代码 (IaC) 管理，将所有环境配置都代码化，保证全球所有区域的环境完全一致。
3. **大规模任务的测试验证难题**：一个 Spark 任务可能需要处理 TB 级数据，运行时间长达数小时，传统的测试方法根本无法适用。我们的解决方案是构建了分层测试体系：单元测试验证单个算子逻辑，集成测试验证小数据集的完整流程，预生产环境验证全量数据的性能和正确性。
4. **依赖管理复杂**：大数据任务依赖大量的内部库和第三方库，版本冲突问题非常严重。我们的解决方案是建立了内部的**Azure Artifacts**私有仓库，统一管理所有依赖的版本，并且在流水线中进行依赖冲突检测。

### 1. 你们为什么选择使用 Docker 和 AKS 来部署大数据任务？和微软传统的 Scope 平台相比有什么优势？

1. **技术栈锁定问题**：Scope 平台是微软专有技术，只能使用 Scope SQL，无法使用开源的 Spark、Flink 等技术，技术生态封闭，人才招聘困难

使用 Docker 和 AKS 的优势：

1. **环境一致性**：Docker 将所有依赖都打包到镜像中，彻底解决了 "在我电脑上能跑，在服务器上跑不了" 的问题
2. **弹性伸缩**：AKS 支持自动扩缩容，能够根据任务的负载自动调整计算资源，高峰期自动扩容，低峰期自动缩容

4. **成本优化**：可以使用 Azure Spot 虚拟机、预留实例等多种成本优化手段，将计算成本降低 50% 以上
5. **统一运维**：所有任务都使用相同的容器化部署方式，运维工具和流程统一，大大降低了运维成本

在我们的项目中，通过将 100 + 个 Scope 任务迁移到 AKS 上的 Spark，我们将整体计算成本降低了 55%，同时任务的平均运行时间缩短了 30%。

### 2. 容器化部署 Spark 任务有哪些挑战？你在微软是怎么解决的？

**参考答案**：

容器化部署 Spark 任务的主要挑战有：

1. **镜像体积过大**：传统的 Spark 镜像包含完整的 Spark 发行版和所有依赖，体积超过 2GB，导致镜像拉取速度很慢，尤其是在跨区域部署的时候。我们的解决方案是使用**多阶段构建**和**分层镜像**技术，将基础镜像、Spark 镜像和业务依赖镜像分开构建，只保留运行时需要的文件，将最终的业务镜像体积减小到了 400MB 以下。
2. **网络性能问题**：AKS 的默认网络插件性能比物理机差，对于网络密集型的 Spark 任务影响很大。我们的解决方案是使用**Azure CNI 网络插件**和**HostNetwork 模式**，让 Pod 直接使用宿主机的网络，网络性能提升了 40% 以上。
3. **本地磁盘空间不足**：Spark 任务在 shuffle 过程中会产生大量的临时数据，很容易导致 Pod 的本地磁盘空间不足。我们的解决方案是使用**Azure Managed Disks**作为 Spark 的本地存储，并且配置了自动磁盘扩容机制，当磁盘使用率超过 80% 时自动扩容。
4. **动态资源分配问题**：Spark 的原生动态资源分配机制在 Kubernetes 上不能很好地工作。我们的解决方案是开发了一个自定义的**Spark Operator**，能够根据任务的实时负载动态调整 Executor 的数量和资源配置，比原生的动态资源分配更加高效和灵活。
5. **跨区域镜像拉取慢**：我们的任务需要部署在全球 10 个 Azure 区域，从中心 ACR 拉取镜像速度很慢。我们的解决方案是使用**ACR 异地复制**功能，将镜像自动同步到所有部署区域的本地 ACR，镜像拉取速度提升了 10 倍以上。

**参考答案**：

我会按照以下标准化流程进行排查，确保在最短时间内恢复业务：

1. **第一步：确认影响范围**（1 分钟）
   - 查看 Azure Monitor 告警信息，确认失败的区域、任务名称和影响范围
   - 检查其他区域的任务是否正常运行，判断是区域性问题还是全球性问题
2. **第二步：查看任务日志**（3 分钟）
   - 登录 Azure Portal，打开 Azure Log Analytics，查询失败任务的详细日志
   - 重点查看错误信息、异常栈和最后执行的操作，初步判断失败原因
3. **第三步：检查基础设施状态**（2 分钟）
   - 查看该区域的 AKS 集群状态，确认是否有节点故障或者资源不足的情况
   - 查看 ADLS 存储和网络的状态，确认是否有 Azure 服务中断
4. **第四步：检查数据状态**（2 分钟）
   - 查看任务依赖的输入数据是否正常，是否存在数据缺失或者数据延迟的情况
   - 检查上游的 Kafka 主题是否有消息堆积
5. **第五步：快速恢复业务**（5 分钟）
   - 如果是代码问题，立即回滚到上一个稳定版本
   - 如果是资源问题，手动增加资源或者将任务调度到其他区域
   - 如果是数据问题，跳过异常数据或者重新拉取数据
6. **第六步：事后复盘**（24 小时内）
   - 对整个事件进行详细复盘，找出问题的根本原因
   - 制定预防措施，避免以后再发生类似的问题
   - 更新运维手册和故障处理流程

3. 瓶颈分析维度不足（扣 1 分）：只说明时长差异，未补充倾斜带来的磁盘溢写、频繁 GC、任务重试等连锁负面影响，排查完整性不足。

## 满分参考答案

该报表为全平台活动效果分析报表，核心逻辑是按活动、地区、时间段、用户标签多维度，统计曝光、点击、下单、支付全链路指标并计算转化类指标。共依赖 5 张核心表：活动维表、用户标签维表、曝光日志表、点击日志表、订单 DWD 明细事实表，单日全量数据约 3TB。

### 一、瓶颈定位

1. 依托 Spark Web UI 查看 DAG 与 Stage 耗时，全作业共 3 个 Shuffle 阶段，第二个 Shuffle 阶段耗时占整体 70%，是核心瓶颈；
2. 查看 Task 运行时长，发现两极分化：10 个 Task 运行超 1 小时，其余仅十余分钟，判定存在严重数据倾斜；
3. 解析 Spark Event Log 日志，统计 Key 分布，定位出 10 个头部活动 ID 为热点 Key，对应订单数据占整体 30%，是倾斜根源；同时观测到该阶段大量数据磁盘溢写、GC 频繁，进一步放大耗时。

### 二、分维度优化及效果

1. 前置过滤：在 SQL 最前端过滤无效曝光、非活动订单、测试数据，输入数据量减少 60%，运行时长缩短 30 分钟；
2. 表分桶优化：将订单事实表、点击日志表统一按`活动ID`分桶，桶数与任务并行度对齐设为 2000，规避 Shuffle 重分区开销，时长再缩短 20 分钟；
3. MapJoin 优化：对体积较小的活动维表启用广播 Join，在 Map 端完成关联，消除 2 个 Shuffle 阶段，时长缩短 15 分钟；
4. 热点倾斜治理：拆分 10 个倾斜活动 ID 单独处理，对热点 Key 追加随机前缀做二次打散，再二次聚合，时长缩短 10 分钟；
5. 资源精细化调优：结合集群水位，将 Executor 数量由 100 调至 400，单 Executor 核数由 2 调至 4，提升整体并行能力，时长缩短 5 分钟。

### 三、核心挑战与解决方案

最大难点：<strong>用户标签维表数据量过大，远超 Spark 默认广播阈值，直接 MapJoin 会引发 Driver OOM</strong>。

解决方案：采用<strong>分片并行 Join</strong>方案，将大维表与主表按统一哈希规则拆分为多个分片，分片内独立执行 Join，最后合并结果；同时搭配分区裁剪，只加载当日增量分区数据，既规避广播上限问题，又不引入额外 Shuffle，彻底解决该卡点。

整体优化后，报表产出时长从 T+2 小时降至 T+45 分钟，任务稳定性也同步提升。

# 第四题：微软 Scope SQL 原有痛点、迁移前整体架构与数据流向

## 面试问题

你在微软主导了 Scope SQL 向 Spark Structured Streaming 的技术栈迁移，请说明：原有 Scope SQL 任务存在哪些核心痛点？迁移前整体任务架构、数据流向是怎样的？

## 优化后考生回答

原有 Scope SQL 全部为离线批量任务，存在多重业务与技术痛点：

1. 执行周期长、资源消耗高，仅支持天级统计产出，无法支撑小时级数据报表，数据时效性差；
2. Scope 属于微软内部私有计算引擎，作业统一运行在 Cosmos 集群。Cosmos 专属集群资源长期紧张，任务高峰期排队超时，且专属集群硬件、服务使用成本偏高，长期运维开销大。

### 迁移前完整架构与数据流向

底层存储采用微软 Cosmos 分布式存储，原始日志、中间计算结果、业务报表全部持久化在 Cosmos；计算层基于私有 Scope SQL 引擎开发，由微软内部统一调度平台定时触发任务。

完整数据链路：原始广告、搜索日志落地 Cosmos 存储 → 调度平台按日调度 Scope 批处理任务 → Scope 引擎读取 Cosmos 数据，完成清洗、聚合、指标统计 → 计算结果回写 Cosmos 分区表持久化 → 下游业务报表、数据分析应用读取 Cosmos 数据对外提供服务。

整套架构纯离线闭环，无消息队列、流式计算能力，全部数据存储、计算依赖微软私有体系。

## 评分 & 尖锐点评（满分 10 分，得分：4/10）

### 扣分核心问题

1. 痛点分析维度单薄（扣 3 分）：仅讲时效、成本、资源紧张，缺少私有技术栈封闭、生态缺失、自定义扩展困难、故障排障效率低等 P7 重点考察的架构痛点。
2. 基础概念混淆（扣 2 分）：口述误将数仓分层 DWS 当作调度系统，属于低级常识错误；早期口述数据流向逻辑颠倒，架构描述层次感不足。
3. 无量化数据支撑（扣 1 分）：未给出任务规模、资源占用、成本增幅等量化指标，论证缺乏说服力。

## 满分参考答案

原有 Scope SQL 是微软内部专属的数据查询计算组件，任务全部为离线批处理作业，长期运行在 Cosmos 存储与计算集群上，核心痛点分为<strong>业务、技术、成本</strong>三大类：

1. <strong>业务时效不足</strong>：所有任务按天调度，仅能产出天级统计数据，无法支撑小时级、准实时的数据查询与监控需求，不能满足广告、搜索业务对数据时效性的要求。
2. <strong>技术栈封闭，扩展性差</strong>：Scope 为私有技术，语法、函数、计算引擎均不对外开源，无法对接 Kafka、Flink 等主流实时组件；自定义逻辑、复杂计算扩展难度大，遇到性能问题无开源方案参考，问题排障效率低。
3. <strong>资源与成本压力</strong>：Cosmos 是公司核心集群，整体资源池紧张，高峰期任务排队严重；且 Cosmos 专属硬件与服务定价高，批量离线任务长期运行，整体硬件与运维成本居高不下。
4. <strong>运维能力薄弱</strong>：原生监控、日志排查、故障重试机制不完善，任务失败后定位根因、恢复业务耗时久，运维成本极高。

### 迁移前整体架构与数据流向

底层存储依托微软 Cosmos 分布式存储，全量原始搜索 / 广告日志、中间结果、最终报表数据均持久化在 Cosmos 中；任务由微软内部统一调度平台进行周期调度，所有计算逻辑通过 Scope SQL 实现。

完整数据流向：

原始搜索 / 广告日志落地至<strong>Cosmos 存储</strong> → 调度平台按天触发 Scope 批处理任务 → Scope 引擎读取 Cosmos 数据完成清洗、转换、聚合统计 → 计算结果回写至 Cosmos 对应分区表 → 下游业务报表、分析应用直接读取 Cosmos 数据对外提供服务。

整套架构纯离线闭环，无中间消息队列、无流式计算链路，所有数据流转、计算、存储均依赖微软私有体系。

During my tenure at Meituan, I worked as a core developer for user and order business domains. I reconstructed the unified order detail fact table on DWD layer, and completed phased migration of all downstream reports. Old non-standard tables ran in parallel with new tables for one full month to guarantee full data consistency before complete decommission. Meanwhile, we integrated the metadata management platform to record metric logic, table lineage and responsible persons, and built an approval workflow for newly added metrics to avoid standard confusion again.

2. End-to-end Spark SQL performance optimization

   The full-platform campaign effect analysis report relied on 5 core tables (campaign dimension table, user label dimension table, exposure log table, click log table and order fact table), processing around 3TB raw data per day with an original 2-hour generation latency.

- Pre-filter invalid data such as non-campaign orders and useless exposure logs, cutting input data volume by 60% and saving 30 minutes of runtime;
- Partition and bucket optimization by campaign ID for order and click tables to eliminate shuffle repartition overhead, shortening runtime by 20 minutes;
- Broadcast small dimension tables via MapJoin to remove two shuffle stages, reducing runtime by 15 minutes;
- Split hot campaign IDs and adopt salting strategy to resolve severe data skew, saving 10 minutes;
- Fine-tune Spark resource configuration to raise parallelism, cutting runtime by another 5 minutes.
